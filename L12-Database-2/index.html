    Reading settings from a properties file

    In plain words
    Don't hard-code the database URL, user name and password in your Java code. Put them in a small text file of key=value lines and read it with java.util.Properties. Then you can point the program at another database, or change the password, without recompiling, and the password isn't sitting in your source code (or on GitHub).

    Slides 3–4

    Statement types

    In plain words
    There are three kinds of statement, each one made by the Connection:
    • Statement (createStatement()): plain SQL text. Fine for fixed SQL with no user input.
    • PreparedStatement (prepareStatement(sql)): SQL with ? gaps that you fill with setString, setInt… Use it whenever values come from the user: it's safe from SQL injection and faster when repeated.
    • CallableStatement (prepareCall(sql)): runs a stored procedure or function that lives inside the database.
    createStatement can also take extra numbers that decide whether the ResultSet can scroll backwards and be edited (next section).

    Statement - Types 3

    • Statements in JDBC abstract the SQL statements
    • Primary interface to the tables in the database
    • Used to create, retrieve, update & delete data (CRUD) from a table
      • Syntax: Statement statement = connection.createStatement();
    • Three types of statements each reflecting a specific SQL statements
      • Statement
      • PreparedStatement allows to write SQL queries with placeholders for input parameters (using ? symbols), which will later be replaced by actual values.
        • This eliminates the need to concatenate strings when including values in SQL queries, which is important for security reasons, particularly to prevent SQL injection attacks.
      • CallableStatement used for executing stored procedures or functions

    Statement - Syntax 4

    • Statement used to send SQL commands to the database
      • Case 1: ResultSet is non-scrollable and non-updateable

    Slides 5–10

    Scrollable and updatable ResultSets

    In plain words
    By default a ResultSet is a one-way, read-only list: you can only call next(). Pass two settings to createStatement to get more:
    • Type: TYPE_FORWARD_ONLY (default, next() only), TYPE_SCROLL_INSENSITIVE (jump anywhere; a frozen snapshot that ignores other people's changes) or TYPE_SCROLL_SENSITIVE (jump anywhere; shows changes others make to the rows).
    • Concurrency: CONCUR_READ_ONLY (default) or CONCUR_UPDATABLE, which lets you change the row under the cursor with updateXxx then save it with updateRow(), delete it with deleteRow(), or add one with moveToInsertRow() … insertRow().
    The demo below shows both sides: what your program's ResultSet holds, and what's actually in the database.

    Scrollable ResultSet 5

    • ResultSet obtained from the statement created using the no argument constructor is:
      • Type forward only (non-scrollable)
      • Not updateable
    • To create a scrollable ResultSet the following statement constructor is required
      • Statement createStatement(int resultSetType, int resultSetConcurrency)
    • ResultSetType determines whether it is scrollable. It can have the following values:
      • ResultSet.TYPE_FORWARD_ONLY
      • ResultSet.TYPE_SCROLL_INSENSITIVE (Unaffected by changes to underlying database)
      • ResultSet.TYPE_SCROLL_SENSITIVE (Reflects changes to underlying database)
      • resultSetHoldability - one of the following ResultSet constants: ResultSet.HOLD_CURSORS_OVER_COMMIT or ResultSet.CLOSE_CURSORS_AT_COMMIT
    • ResultSetConcurrency determines whether data is updateable. Its possible values are
      • CONCUR_READ_ONLY
      • CONCUR_UPDATEABLE
    • Not all database drivers may support these functionalities

    Scrollable ResultSet 6

    ConstantMeaning

    Database metadata
    
  
    
  
    In plain words
    Lecture 11 used ResultSet metadata (rs.getMetaData()) to learn about the columns of one query. Database metadata (connection.getMetaData()) describes the whole database: which product and version it is, which driver you're using, and which tables, keys and procedures exist. Most of its methods answer with a ResultSet, which you read with the usual while (rs.next()) loop.

    Slides 14–18
    
    
    PreparedStatement
    
  
    
  
    In plain words
    Write the SQL once with a ? where each value goes, then fill the gaps with setString(position, value), setInt(…) and so on. Positions count from 1, left to right. Then call executeQuery() or executeUpdate() with no arguments. The database receives the SQL and the values separately, so a value can never change the meaning of the SQL. That's what stops SQL injection, and it also means quotes in names like O'Brien just work.
    

  
    
    
    Prepared Statement 14
    
    
    Main Idea: Prepare query in advance with a host variable, denoted by ?, that is filled with a different value every time the query is run.
    
    
    The host variable must be bound to an actual value of a field, and this is performed by a set function similar to the get function discussed earlier.
    
    
    • PreparedStatement provides a means to create a reusable statement that is precompiled by the database
    
    
    String publisherQuery =
 "SELECT Books.Price, Books.Title " +
 "FROM Books, Publishers " +
 "WHERE Books.Publisher_Id=Publishers.Publisher_Id AND" +
 "Publishers.Name = ?";

PreparedStatement publisherQueryStmt =
  con.prepareStatement(publisherQuery);

publisherQueryStmt.setString(1, publisher);
rs = publisherQueryStmt.executeQuery();
    
    
    1st argument is host variable we want to set, 2d argument value to be assigned to host variable; position 1denotes first ?
    
  
    

  
    
    
    Prepared Statement 15
    
    
      
      
    • It has three main uses
        
      • Create parameterized statements such that data for parameters can be dynamically substituted
      • Create statements where data values may not be character strings
      • Precompiling SQL statements to avoid repeated compiling of the same SQL statement
      • 
      
    • If parameters for the query are not set the driver returns an SQL Exception
      • 
      
    • Only the no parameters versions of executeUpdate() and executeQuery() allowed with prepared statements.
      •

    • Example

    Slides 19–21
    
    
    Stored procedures and CallableStatement
    
  
    
  
    In plain words
    A stored procedure is a small named program saved inside the database, like a method you call by name. Java runs it with a CallableStatement: con.prepareCall("{call name(?, ?)}"). Each ? is a parameter: IN parameters are filled with setXxx like a PreparedStatement; OUT parameters are announced with registerOutParameter(position, type) before execute() and read afterwards with getXxx(position). The catch: each database has its own procedure language, so your SQL stops being portable.
    

  
    
    
    Callable Statements & Stored Procedures 19
    
    
      
      
    • Stored Procedures
        
      • Are procedures that are stored in a database.
      • Consist of SQL statements as well as procedural language statements
      • May (or may not) take some arguments
      • May (or may not) return some values
      • 
      
    • Advantages of Stored Procedures
        
      • Encapsulation & Reuse
      • Transaction Control
      • Standardization
      • 
      
    • Disadvantages
        
      • Database specific (lose independence)
      • 
      
    • Callable statements provide means of using stored procedures in the database
      • 
    
    
  
    

  
    
    
    Callable Statements & Stored Procedures 20
    
    
      
      
    • Stored Procedures must follow certain rules
        
      • Names of the stored procedures and parameters must be legal
      • Parameter types must be legal supported by database
      • Each parameter must have one of In, Out or Inout modes
      • 
      
    • Example
      • 
    
    
    
    // Creating a stored procedure using SQL
    CREATE PROC procProductsList AS SELECT * FROM Products;

CREATE PROC procProductsDeleteItem(inProductsID LONG) AS DELETE
FROM Products WHERE ProductsID = inProductsID;"

CREATE PROC procProductsAddItem(inProductName VARCHAR(40),
inSupplierID LONG, inCategoryID LONG) AS INSERT INTO Products
(ProductName, SupplierID, CategoryID) Values (inProductName,
inSupplierID, inCategoryID);"

CREATE PROC procProductsUpdateItem(inProductID LONG,
inProductName VARCHAR(40)) AS UPDATE Products SET ProductName =
inProductName WHERE ProductID = inProductID;"
    
    
    Usage: procProductsUpdateItem(1000, "My Music")
    
    
    (Sets the name of the product with id 1000 to 16.99)
    
  
    

  
    
    
    Callable Statements & Stored Procedures 21
    
    
    String sql = "{call getEmployeeSalary(?, ?)}"; // SQL calling a stored procedure with parameters

CallableStatement callableStatement = connection.prepareCall(sql);
callableStatement.setInt(1, 101);   // Input parameter: employee ID
callableStatement.registerOutParameter(2, Types.DECIMAL); // Output parameter: salary

callableStatement.execute(); // Execute the stored procedure

double salary = callableStatement.getDouble(2); // Get the output parameter (salary)
System.out.println("Employee Salary: " + salary);
    
    
    CREATE FUNCTION get_salary(emp_id INT) RETURNS DECIMAL(10, 2)
BEGIN
    DECLARE total DECIMAL(10, 2);
    SELECT salary INTO total FROM employees WHERE id = emp_id;
    RETURN total;
END;

CREATE PROCEDURE get_employee_salary(IN emp_id INT, OUT total_salary DECIMAL(10, 2))
BEGIN
    SELECT salary INTO total_salary FROM employees WHERE id = emp_id;
END;
    
  
    

  
    Guide noteSlide 20's CREATE PROC … AS syntax and the LONG type are MS Access / SQL Server style; slide 21's CREATE FUNCTION/CREATE PROCEDURE … BEGIN … END is MySQL style. That's the "database specific" disadvantage from slide 19 in action. Small slip-ups: slide 20 mixes ProductsID and ProductID, the stray " at the ends of lines shouldn't be there, and the usage line sets the name to "My Music", not 16.99. On slide 21 the Java calls getEmployeeSalary but the procedure is named get_employee_salary; the names must match. A function is called with "{? = call get_salary(?)}", where the first ? is the return value (register it as OUT).

    Slides 22–23
    
    
    Transactions
    
  
    
  
    In plain words
    A transaction is "all or nothing". Moving 100 JD from Lina to Omar takes two UPDATEs; if the program dies between them, the money must not vanish. Normally every statement is saved the moment it runs (auto-commit). Turn that off with con.setAutoCommit(false), run your statements, then con.commit() to make them all permanent, or con.rollback() to undo all of them since the last commit.
    

  
    
    
    Transactions 22
    
    
    A transaction is a group of statements that will be committed if all goes well, or all rolled back if an error occurs.
    
    
    They are needed to support database integrity: e.g. when adding a record, we want to be sure that all tables containing information on that record have indeed been updated; if some have not, the entire transaction should be rolled back.
    
    
    By default a database connection is in autocommit mode, i.e. each SQL command is committed as soon as executed. Thus, for transaction management, we first need to turn off the autocommit mode:
    
    
    con.setAutoCommit(false);
Statement stmt=con.creatStatement();
stmt.executeUpdate(command1);
stmt.executeUpdate(command2);
…
con.commit(); //if all goes well
con.rollback();//if error occurs
    
  
    

  
    
    
    Transactions and JDBC 23
    
    
      
      
    • JDBC allows SQL statements to be grouped together into a single transaction
      • 
      
    • Transaction control is performed by the Connection object, default mode is auto-commit, I.e., each sql statement is treated as a transaction
      • 
      
    • We can turn off the auto-commit mode with con.setAutoCommit(false);
      • 
      
    • And turn it back on with con.setAutoCommit(true);
      • 
      
    • Once auto-commit is off, no SQL statement will be committed until an explicit is invoked con.commit();
      • 
      
    • At this point all changes done by the SQL statements will be made permanent in the database.
      •

    Slides 24–31
    
    
    Batch execution
    
  
    
  
    In plain words
    Sending 1,000 INSERTs one by one means 1,000 trips to the database and back. A batch collects them first: for each row, set the ? values and call addBatch(); then one executeBatch() sends them all together and returns an int[] with the row count of each one. Turn auto-commit off first and commit() at the end, so the whole batch is saved or none of it is.
    

  
    
    
    Batch Execution 24
    
    
      
      
    • A JDBC feature that allows executing multiple SQL statements as a group
      • 
      
    • Reduces the number of round-trips to the database
      • 
      
    • Useful for inserting/updating large sets of records
      • 
      
    • Great performance improvement over single-row executions
      • 
    
    
    
    When to Use It
    
    
      
      
    • Importing data (CSV, Excel, JSON)
      • 
      
    • Saving many rows from a Swing JTable
      • 
      
    • Periodic data syncing
      • 
      
    • Bulk updates or deletes
      • 
      
    • Logging / auditing
      • 
    
    
  
    

  
    
    
    How Batch Execution Works 25
    
    
      
      
    • Create a PreparedStatement
      • 
      
    • Loop through data
      • 
      
    • For each record, set parameters
      • 
      
    • Call addBatch()
      • 
      
    • After loop, call executeBatch()
      • 
      
    • Commit the transaction
      • 
    
    
  
    

  
    
    
    How Batch Execution Works 26
    
    
    Connection conn = DriverManager.getConnection(url, user, pass);
String sql = "INSERT INTO students(name, age) VALUES(?, ?)";

PreparedStatement ps = conn.prepareStatement(sql);
conn.setAutoCommit(false);

for (Student s : students) {
    ps.setString(1, s.getName());
    ps.setInt(2, s.getAge());
    ps.addBatch();
}

ps.executeBatch();
conn.commit();
    
  
    

  
    
    
    Error Handling 27
    
    
      
      
    • Wrap batch execution in try-catch
      • 
      
    • On exception:
      conn.rollback();
      • 
      
    • Log failed batch indices
      • 
      
    • Avoid mixing huge batches (split into chunks of 500–1000)
      • 
    
    
  
    

  
    
    
    Best Practices 28
    
    
      
      
    • Always use PreparedStatement, not Statement
      • 
      
    • Disable auto-commit while batching
      • 
      
    • Tune batch size (100–1000 is usually ideal)
      • 
    
    
  
    

  
    
    
    saveBatch 29
    
    
    public void saveBatch(List<MyData> dataList) {
    String sql = "INSERT INTO students (name, age) VALUES (?, ?)";

    try (Connection conn = DriverManager.getConnection(DB_URL, USER, PASS);
         PreparedStatement ps = conn.prepareStatement(sql)) {

        conn.setAutoCommit(false); // required for batch

        for (MyData data : dataList) {
            ps.setString(1, data.getName());
            ps.setInt(2, data.getAge());

            ps.addBatch(); // add to batch
        }

        int[] result = ps.executeBatch(); // execute batch
        conn.commit();

        System.out.println("Inserted rows: " + result.length);

    } catch (SQLException e) {
        e.printStackTrace();
    }
}

    Slide 32
    
    
    Handling errors
    
  
    
  
    In plain words
    Almost every JDBC method can throw SQLException. The pattern that keeps the database consistent: do the work and commit() in try; rollback() in catch; close() in finally.
    

  
    
    
    Handling Errors with Exceptions 32
    
    
      
      
    • Programs should recover and leave the database in a consistent state.
      • 
      
    • If a statement in the try block throws an exception or warning, it can be caught in one of the corresponding catch statements
      • 
      
    • How might a finally {…} block be helpful here?
        
      • E.g., you could rollback your transaction in a catch { …} block or close database connection and free database related resources in finally {…} block
      • 
    
    
  
    

  
    
    
    Added · the whole pattern in one place
    
    
    Connection conn = null;
PreparedStatement ps = null;
try {
   conn = DriverManager.getConnection(url, user, password);
   conn.setAutoCommit(false);                       // start a transaction
   ps = conn.prepareStatement("UPDATE accounts SET balance = balance + ? WHERE id = ?");
   ps.setDouble(1, -100); ps.setInt(2, 1); ps.executeUpdate();
   ps.setDouble(1,  100); ps.setInt(2, 2); ps.executeUpdate();
   conn.commit();                                   // all went well: make it permanent
} catch (SQLException e) {
   System.out.println("Error " + e.getErrorCode() + " (" + e.getSQLState() + "): " + e.getMessage());
   try { if (conn != null) conn.rollback(); }      // undo everything since the last commit
   catch (SQLException ex) { ex.printStackTrace(); }
} finally {
   try {                                            // always free the resources
      if (ps != null) ps.close();
      if (conn != null) conn.close();
   } catch (SQLException ex) { ex.printStackTrace(); }
}
    
    
    
      
    
        
    SQLException methodGives you
    
        
          
    getMessage()The database's description of the error.
    
          
    getErrorCode()The vendor's own error number (e.g. MySQL 1045 = access denied).
    
          
    getSQLState()A standard five-character code (e.g. 23000 = constraint violation).
    
          
    getNextException()The next error in a chain, if several happened.
    
            
      
    
    
    
    
    "Warnings" are not thrown: they're attached to the Connection, Statement or ResultSet as an SQLWarning; read them with getWarnings().
